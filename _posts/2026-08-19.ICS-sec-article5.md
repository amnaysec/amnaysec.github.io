A SIEM is only as good as its rules. Wazuh ships with a large set of native rules 
that cover common Windows events, authentication failures, file integrity violations, 
and a lot of other generic scenarios. None of them were written with a seven-phase 
ransomware attack on an OT engineering station in mind.

This article covers the detection logic built on top of the Wazuh and Sysmon 
infrastructure described in the previous articles. Each rule targets a specific 
phase of the attack vector, and each maps to a MITRE ATT&CK technique. The goal 
is not just to alert. It is to alert on the right thing, at the right level of 
criticality, with enough context for an analyst to understand what happened without 
digging through raw logs.

## How Wazuh Detection Works

Before getting into the rules themselves, it helps to understand the processing 
pipeline. When an event arrives at the Wazuh Manager from an agent, it goes through 
two stages.

The first stage is decoding. A decoder parses the raw event and extracts structured 
fields from it. For Sysmon events transmitted via the `eventchannel` format, Wazuh 
already has native decoders that extract fields like `win.eventdata.targetFilename`, 
`win.eventdata.commandLine`, `win.eventdata.targetObject`, and 
`win.eventdata.destinationPort`. No custom decoders are needed here. The Sysmon 
telemetry arrives already structured.

The second stage is rule matching. Rules evaluate the structured fields extracted 
by the decoders and fire alerts when their conditions are met. Rules have a severity 
level from 1 to 15. Level 15 is the maximum and is the threshold that triggers 
Active Response automatically in this setup.

All custom rules live in `/var/ossec/etc/rules/local_rules.xml` on the Wazuh 
Manager. They are grouped under a `wannacry,ransomware` group tag for easy 
filtering in the Dashboard.

## Rule 100004 - Shadow Copy Deletion (T1490)

This is the most critical rule in the set, because Phase 1 of the attack vector 
executes first and fastest. Sysmon captures `vssadmin.exe` being launched with 
the `delete shadows /all /quiet` arguments via Event ID 1 (ProcessCreate). The 
rule matches on the `commandLine` field using a regex pattern.

```xml
<rule id="100004" level="15">
  <if_group>sysmon</if_group>
  <field name="win.eventdata.commandLine"
         type="pcre2">vssadmin.*delete.*shadows</field>
  <description>Ransomware: Shadow copy deletion 
  attempt detected (T1490)</description>
  <mitre><id>T1490</id></mitre>
</rule>
```

Level 15 here is not arbitrary. Shadow copy deletion is a near-certain indicator 
of ransomware. There is no legitimate administrative scenario in this OT environment 
where an engineer would run `vssadmin delete shadows /all` from a PowerShell 
session. The rule fires, the Active Response triggers, and the process tree gets 
killed before Phase 2 can start.

## Rule 100008 - System Recovery Disabled (T1490)

`bcdedit /set recoveryenabled No` is the companion command to `vssadmin`. It 
disables the Windows Recovery Environment, making it impossible to boot into 
repair mode after a ransomware encryption. Same technique, same MITRE ID, slightly 
lower criticality because it is less immediately destructive than shadow copy 
deletion.

```xml
<rule id="100008" level="14">
  <if_group>sysmon</if_group>
  <field name="win.eventdata.commandLine"
         type="pcre2">bcdedit.*recoveryenabled</field>
  <description>Ransomware: System recovery 
  disabled (T1490)</description>
  <mitre><id>T1490</id></mitre>
</rule>
```

## Rule 100005 - C2 Beacon (T1071)

Phase 2 opens a TCP connection to port 9999 from PowerShell. Sysmon Event ID 3 
(NetworkConnect) captures outbound connections with the initiating process. The 
rule matches on both the destination port and the process name, because port 9999 
alone is not a reliable signal (plenty of legitimate applications use arbitrary 
high ports). The combination of port 9999 and `powershell.exe` as the initiating 
process is specific enough to be meaningful.

```xml
<rule id="100005" level="14">
  <if_group>sysmon</if_group>
  <field name="win.eventdata.destinationPort">9999</field>
  <field name="win.eventdata.image"
         type="pcre2">powershell\.exe</field>
  <description>Ransomware: Suspicious C2 connection 
  from PowerShell (T1071)</description>
  <mitre><id>T1071</id></mitre>
</rule>
```

## Rule 100003 - Registry Persistence (T1547.001)

Phase 3 writes to `CurrentVersion\Run` keys from PowerShell. Sysmon Event ID 13 
(RegistryEvent) captures registry value modifications with the responsible process. 
The rule matches on the target key path and the process image simultaneously.

```xml
<rule id="100003" level="15">
  <if_group>sysmon</if_group>
  <field name="win.eventdata.targetObject"
         type="pcre2">CurrentVersion\\Run</field>
  <field name="win.eventdata.image"
         type="pcre2">powershell\.exe</field>
  <description>Ransomware: Run key modified 
  by PowerShell (T1547.001)</description>
  <mitre><id>T1547.001</id></mitre>
</rule>
```

Modifications to `CurrentVersion\Run` by legitimate processes happen regularly 
during software installations. What makes this alert meaningful is the 
`powershell.exe` filter. A software installer does not write autorun keys from 
a PowerShell session. An attacker does.

## Rule 100001 - Encrypted File Creation (T1486)

Phase 4 creates `.WNCRY` files via Sysmon Event ID 11 (FileCreate). The rule 
matches on the `targetFilename` field using a regex that catches any file ending 
with `.WNCRY`.

```xml
<rule id="100001" level="15">
  <if_group>sysmon</if_group>
  <field name="win.eventdata.targetFilename"
         type="pcre2">\.WNCRY$</field>
  <description>Ransomware: Encrypted file 
  created on OT station (T1486)</description>
  <mitre><id>T1486</id></mitre>
</rule>
```

In this specific experiment, rule 100001 did not fire during the attack run. The 
reason is not a configuration error. The Active Response triggered by rule 100004 
(shadow copy deletion) killed the PowerShell process tree before Phase 4 started. 
The rule is correct. The attack was stopped before it reached the encryption phase. 
That is a result, not a failure.

## Rule 100006 - SMB Scan (T1021.002)

Phase 6 opens TCP connections to port 445 across the subnet from PowerShell. 
The rule matches on the destination port and the initiating process.

```xml
<rule id="100006" level="12">
  <if_group>sysmon</if_group>
  <field name="win.eventdata.destinationPort">445</field>
  <field name="win.eventdata.image"
         type="pcre2">powershell\.exe</field>
  <description>Ransomware: SMB scan from 
  PowerShell (T1021.002)</description>
  <mitre><id>T1021.002</id></mitre>
</rule>
```

Level 12 rather than 15 here, because PowerShell connecting to port 445 is less 
unambiguous than shadow copy deletion. In a production environment with more 
context, this rule would benefit from a frequency condition: fire only if the same 
process connects to port 445 on more than N distinct hosts within a given time 
window. That refinement is left as a tuning exercise for a real deployment.

## The Full Rule Set and MITRE Mapping

| Rule ID | Phase | Behavior | Sysmon Event | Level | MITRE |
|---|---|---|---|---|---|
| 100004 | 1 | `vssadmin delete shadows` | ID 1 | 15 | T1490 |
| 100008 | 1 | `bcdedit recoveryenabled No` | ID 1 | 14 | T1490 |
| 100005 | 2 | C2 beacon port 9999 | ID 3 | 14 | T1071 |
| 100003 | 3 | Run key written by PowerShell | ID 13 | 15 | T1547.001 |
| 100001 | 4 | `.WNCRY` file created | ID 11 | 15 | T1486 |
| 100006 | 6 | SMB scan from PowerShell | ID 3 | 12 | T1021.002 |

Every rule in this set is behavioral. None of them match on a file hash, a binary 
name, or any artifact specific to WannaCry. They match on actions. A different 
ransomware that deletes shadow copies, writes persistence keys from PowerShell, 
and creates encrypted files with a custom extension would fire exactly the same 
rules. That generality is the point.

## A Note on False Positives

During the attack run, a rule 92213 alert fired before any of the custom rules. 
It flagged a file named `PSScriptPolicyTest` dropped in `AppData\Local\Temp` by 
PowerShell. This is a Windows mechanism: when PowerShell starts, it creates a 
temporary file to test the execution policy before running the actual script. The 
SwiftOnSecurity Sysmon configuration catches this as a suspicious file drop, and 
the native Wazuh rule 92213 fires at level 15.

This is a textbook false positive. The alert is technically correct (a file was 
dropped in a suspicious location by PowerShell), but the trigger has nothing to 
do with malicious intent. In a production SOC, this kind of alert would generate 
noise every time an engineer runs a legitimate PowerShell script. Managing that 
noise without missing real threats is one of the core challenges of OT security 
monitoring, and it is discussed in the final article of this series.
