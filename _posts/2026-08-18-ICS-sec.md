Every security project starts with an architecture decision. Before writing a single 
detection rule or running any attack scenario, I had to answer a basic question: 
what does the environment look like, and why does it look that way?

This article covers the physical setup, the network topology, and the component 
choices behind the supervision infrastructure I built at OCP Group's Daoui Washing 
Plant. Nothing here is theoretical. Every decision has a concrete reason behind it.

## Two Machines, One Isolated Network

The environment is built around two physically independent machines connected on a 
dedicated industrial network segment with no internet access and no connection to 
any enterprise network.

The first machine runs Xubuntu 24.04 LTS and hosts the full Wazuh stack: Manager, 
Indexer, and Dashboard. It is the supervision server. Its job is to receive events, 
apply detection rules, generate alerts, and trigger automated responses.

The second machine runs Windows 10 Pro. It plays the role of an OT engineering 
station: it holds industrial configuration files, SCADA supervision data, process 
schemas, and PLC parameters. A Wazuh agent and Sysmon run on it silently, 
collecting and forwarding events to the Manager.

![Industrial Network Topology](/assets/img/posts/wazuh_project/Napkin6.png)
*Figure 1 - The two machines sit on an isolated 192.168.100.0/24 network with no 
default gateway toward the outside. The supervision server is at .10, the OT 
station at .20.*

The addressing is fixed and static on both machines. There is no DHCP involved. 
The Wazuh Manager needs a stable, known IP because every agent registration and 
every active response command is sent to that address. Letting it float would break 
the entire chain.

| Machine | OS | IP | Role |
|---|---|---|---|
| Supervision Server | Xubuntu 24.04 | 192.168.100.10 | Wazuh Manager + Indexer + Dashboard |
| OT Engineering Station | Windows 10 Pro | 192.168.100.20 | Wazuh Agent + Sysmon + Target |

Connectivity between the two machines was validated with bidirectional ping tests 
before any software was installed.

## Why Isolation Matters Here

Running attack scenarios on a network that has any path to the outside is a bad 
idea. WannaCry-like behavior includes active SMB scanning across the local subnet. 
If that subnet has a route somewhere, the scan goes somewhere. Keeping the network 
fully isolated is not just a safety measure for this project. It reflects how OT 
networks are supposed to be architected in production: segmented, with no direct 
path between the industrial layer and the corporate network.

The IEC 62443 standard and NIST SP 800-82 both make this point explicitly. The 
segmentation in this lab is not a simulation of good practice. It is good practice.

## The Communication Flow

The data flow between the two machines follows a single direction for the most part. 
The OT station generates events, the supervision server processes them.

![Communication Flows Between Machines](/assets/img/posts/wazuh_project/napkin7.png)
*Figure 4 - Sysmon captures events on the OT station. The Wazuh agent forwards 
them encrypted to the Manager on TCP 1514. The Indexer stores everything on port 
9200. The Dashboard exposes it on HTTPS 443.*

Three ports matter in this setup:

- **TCP 1514** is the agent-to-manager communication channel. All events travel 
this way, encrypted.
- **TCP 9200** is the internal link between the Manager and the OpenSearch Indexer. 
This is where alerts get stored and indexed.
- **HTTPS 443** is the Dashboard port. This is where you actually look at what is 
happening.

Active response commands travel the reverse path: Manager to agent over the same 
1514 channel. When a rule fires and triggers a response, the Manager pushes the 
command down to the agent on the OT station, which executes the remediation script 
locally.

## Why Wazuh

The choice of Wazuh was not arbitrary. The alternatives were either expensive 
(Splunk, QRadar), limited in their native response capabilities (ELK Stack has no 
built-in active response), or not open-source. Wazuh covers the full loop: log 
collection, correlation, alerting, MITRE ATT&CK mapping, and automated response, 
all in a single deployable stack at no licensing cost.

| Tool | Open-source | Active Response | MITRE ATT&CK | Cost |
|---|---|---|---|---|
| Wazuh | Yes | Yes | Yes | Free |
| Splunk | No | Yes | Yes | High |
| QRadar | No | Yes | Yes | Very high |
| ELK Stack | Yes | No native | Partial | Free |

For an OT environment where operational continuity 
is non-negotiable, Wazuh is a credible first layer of defense. It is not a full EDR. 
It does not do deep packet inspection. But it does behavioral analysis on endpoint 
events, which is exactly what this project needs.

## Why Sysmon Is Non-Negotiable

Windows native event logs are not enough for behavioral detection. They tell you 
that something happened. They do not always tell you what process caused it, what 
the parent process was, or what network connection was initiated at the same time.

Sysmon fills that gap. Deployed with the SwiftOnSecurity configuration, which is 
the community reference for balancing coverage and noise, it adds a layer of 
telemetry that Wazuh can actually use to build detection logic.

The Event IDs that matter for this project are:

| Event ID | Name | What it captures |
|---|---|---|
| 1 | ProcessCreate | Every new process with full command line and parent |
| 3 | NetworkConnect | TCP/UDP connections initiated by processes |
| 11 | FileCreate | New files created on the filesystem |
| 13 | RegistryEvent | Registry value modifications |
| 23 | FileDelete | File deletions |

Without Sysmon, none of the detection rules described in later articles would work. 
The native Windows logs simply do not expose this level of detail in a format that 
Wazuh can parse and correlate efficiently.

## What the OT Station Actually Contains

The Windows 10 machine is not just a generic target. It holds a structured set of 
industrial assets organized under `C:\IndustrialAssets\`, split into four 
categories that reflect what a real OT engineering station would carry.

- `config\` holds PLC configuration files for reactors and pumps: operating speeds, 
maximum temperatures, pressure thresholds, Modbus network parameters. Extensions 
are `.plc` and `.cfg`.
- `scada\` holds HMI screen configurations, tag databases (temperature, pressure, 
flow rate), and supervision views. Extensions are `.scada`, `.hmi`, `.xml`.
- `process\` holds sensor measurement histories and operational databases. 
Extensions are `.csv` and `.db`.
- `schemas\` holds P&ID drawings and safety procedures signed off by the chief 
engineer. Extensions are `.dwg` and `.pdf`.

![Industrial Assets File Tree](/assets/img/posts/wazuh_project/screen_12_industrial_assets.png)
*Figure 5 - The industrial assets directory on the OT engineering station. These 
files are the actual targets of the attack scenario.*

The reason this matters is not cosmetic. A real ransomware attack on an OT 
engineering station does not just encrypt random documents. It encrypts the files 
that an engineer needs to reconfigure an automaton after a failure, the schemas 
needed to understand the process, the historical data used for predictive 
maintenance. Losing those files in a real incident has operational consequences 
that go well beyond a data recovery problem.
