Before writing a single detection rule, I needed something to detect. That meant 
designing an attack scenario that is realistic enough to generate meaningful IOCs, 
controlled enough to run safely in an isolated environment, and honest enough to 
acknowledge what it is and what it is not.

This article covers two things: what the OT engineering station actually contains 
and why it is a credible target, and how the attack vector was designed to 
reproduce WannaCry's behavioral fingerprint without using the real malware.

## What the OT Station Contains

The Windows 10 machine is not a generic target. It holds a structured set of 
industrial assets under `C:\IndustrialAssets\`, organized into four categories 
that reflect what a real OT engineering station carries in a phosphate processing 
environment.

`config\` holds PLC configuration files for reactors and pumps: operating speeds, 
maximum temperatures, pressure thresholds, Modbus network parameters. These are 
the files an engineer opens when a production parameter needs to change or when 
an automaton needs to be reconfigured after a failure. Extensions are `.plc` 
and `.cfg`.

`scada\` holds HMI screen configurations, tag databases (temperature, pressure, 
flow rate readings), and supervision view definitions. Extensions are `.scada`, 
`.hmi`, `.xml`.

`process\` holds sensor measurement histories and operational databases. These 
are used for trend analysis, anomaly detection, and predictive maintenance. 
Extensions are `.csv` and `.db`.

`schemas\` holds P&ID drawings and safety procedures validated by the chief 
engineer. Extensions are `.dwg` and `.pdf`.

![Industrial Assets on the OT Station](/assets/img/posts/wazuh_project/screen_12_industrial_assets.png)
*Figure 1 - The industrial assets directory on the OT engineering station, 
organized by category.*

The reason this structure matters is not cosmetic. When a ransomware hits an OT 
engineering station in a real incident, it is not encrypting random office 
documents. It is encrypting the files that an engineer needs to bring a stopped 
automaton back online, the schemas needed to understand the process state, the 
historical data used to justify a maintenance decision. The operational impact 
goes well beyond a data recovery problem.

![OT Station and Its Critical Assets](/assets/img/posts/wazuh_project/napkin8.png)
*Figure 2 - The OT engineering station sits at the intersection between the 
supervision layer and the physical process. Compromising it means losing visibility 
and control simultaneously.*

## Why Not Use the Real WannaCry

Using the actual WannaCry binary was ruled out early for three reasons.

First, the propagation mechanism. WannaCry exploits EternalBlue (MS17-010) to 
spread automatically across SMB-exposed networks. Even in an isolated environment, 
an uncontrolled propagation would compromise the experiment's reproducibility and 
introduce risks that are unnecessary for what we are trying to demonstrate.

Second, legal and ethical constraints. Possessing and executing real malware in 
an academic or professional project context carries obligations that go beyond 
technical precautions.

Third, and most importantly: it is not needed. The goal of this project is not 
to reproduce WannaCry exactly. It is to generate the behavioral IOCs that Wazuh 
needs to fire detection rules. A custom PowerShell script that replicates those 
behaviors precisely serves that purpose better than the real malware, because it 
gives full control over the sequence, the timing, and the artifacts produced.

| Approach | Advantages | Drawbacks | Decision |
|---|---|---|---|
| Real WannaCry | Identical IOCs | Legal risk, uncontrolled propagation, killswitch | Rejected |
| Custom behavioral vector | Full control, reproducible, safe | Not 100% identical to real malware | Retained |

## The Seven-Phase Attack Vector

The attack vector is a PowerShell script that executes seven phases sequentially 
with no delay between them, replicating the speed of a real ransomware execution. 
Each phase maps to one or more MITRE ATT&CK techniques and generates specific 
Sysmon events that the detection rules will target.

![Attack Vector Execution Phases](/assets/img/posts/wazuh_project/napkin9.png)
*Figure 3 - The seven phases of the attack vector, from shadow copy deletion to 
lateral movement attempt.*

**Phase 1 - Shadow copy deletion (T1490)**

The first action is the most destructive and the most telling. Before doing 
anything else, the script runs `vssadmin delete shadows /all /quiet`, `bcdedit 
/set recoveryenabled No`, and `wbadmin delete catalog`. These three commands 
destroy Windows shadow copies, disable system recovery, and remove the backup 
catalog. Each of them executes in under a second. By the time any monitoring 
system has processed the event, the backups are already gone.

This is not an accident of script design. Real ransomware operators put this 
phase first deliberately. Destroying recovery options before encrypting files 
maximizes the victim's dependence on the attacker for data restoration.

**Phase 2 - C2 beacon (T1071)**

A TCP connection is opened toward the supervision server at `192.168.100.10:9999`, 
where a listener is running. The script sends a beacon string identifying the 
compromised station and waits for a command response. This simulates the initial 
check-in that real malware performs with its command and control infrastructure 
after gaining execution on a new host.

**Phase 3 - Registry persistence (T1547.001)**

Three keys are written into `HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\Run` 
and `HKCU\SOFTWARE\Microsoft\Windows\CurrentVersion\Run`, using names that 
impersonate legitimate Windows services. This ensures the malware survives a 
reboot. Sysmon captures this via Event ID 13 (RegistryEvent), and the process 
responsible for the write (PowerShell) is recorded alongside the target key path.

**Phase 4 - File encryption (T1486)**

This is the core of the ransomware behavior. For each file under 
`C:\IndustrialAssets\`, the script reads the original content, applies XOR 
encryption with a fixed key and prepends a `WANACRY!` header, writes the 
encrypted result to a new file with the `.WNCRY` extension, and deletes the 
original. This two-step process (create new, delete original) is exactly how 
WannaCry operates, and it is what makes Sysmon Event ID 11 (FileCreate) and 
Event ID 23 (FileDelete) the right signals to watch.

The XOR encryption used here is simpler than WannaCry's AES-128, but that 
difference is irrelevant for detection purposes. Wazuh is not analyzing the 
encrypted content. It is watching the filesystem behavior: a PowerShell process 
creating `.WNCRY` files and deleting the originals at speed.

**Phase 5 - Ransom note (T1486)**

A text file named `!WNCRYInstructions.txt` is written to `C:\IndustrialAssets\` 
and to the engineer's desktop. Sysmon captures this as another FileCreate event 
(Event ID 11). The content of the note is consistent with real ransomware demands 
and references the industrial context of the station.

**Phase 6 - SMB network scan (T1021.002)**

The script attempts TCP connections to port 445 across the first 50 addresses of 
the `192.168.100.0/24` subnet, starting with the known hosts (`.20` and `.10`) 
to guarantee at least one successful connection that Sysmon will log via Event 
ID 3 (NetworkConnect). This replicates WannaCry's lateral movement reconnaissance 
behavior.

**Phase 7 - Lateral movement attempt (T1021.002)**

For each host where port 445 was found open, the script attempts to access the 
administrative share `\\target\C$`. This simulates the propagation attempt that 
WannaCry would execute via EternalBlue on a vulnerable machine.

## The IOCs This Generates

Every phase produces observable artifacts. The table below maps each phase to 
its Sysmon event and the detection rule it will feed.

| IOC | Type | Sysmon Event ID | Phase |
|---|---|---|---|
| `vssadmin delete shadows` execution | Process | 1 | 1 |
| `bcdedit recoveryenabled No` execution | Process | 1 | 1 |
| TCP connection to port 9999 from PowerShell | Network | 3 | 2 |
| Run key modified by PowerShell | Registry | 13 | 3 |
| `.WNCRY` files created | File | 11 | 4 |
| Original files deleted | File | 23 | 4 |
| `!WNCRYInstructions.txt` created | File | 11 | 5 |
| TCP connections to port 445 from PowerShell | Network | 3 | 6 |

These are the signals that the next article builds detection rules around. Each 
row in this table corresponds to a Wazuh rule that will fire when the behavior 
occurs, regardless of what binary produced it.

Part 5 covers the detection rules themselves: how they are written, what each 
one targets, and how they map to the MITRE ATT&CK framework.
